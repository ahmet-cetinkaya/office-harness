# Plan: Scheduled directives (0025)

## Summary

A new `schedule` module keeps the person's schedules, their next due times, and their last 20 run results. A server task, the scheduler, wakes every 5 seconds, waits for the 0017 sweep gate, and for each schedule that is on handles the due times: a due time that is at most 2 minutes old becomes a run, an older one becomes one missed entry. A run goes through new "scheduled" entry points of the existing hold guard, the 0012 queue, and the 0018 wake, all with a new actor, `Actor::Schedule`. The desktop app gets a Schedules dialog and one more field in the limits dialog. Scheduled temps are a follow-up change (review decision); this plan leaves the hooks they need (the scheduler, the actor, the notification) and builds none of the temp parts.

**What you get:**
- Module `schedule` (domain: repeat and due-time rules on `jiff`; application: save, switch, delete, scheduler round, run settle; infrastructure: SQLite; presentation: `schedule.*` requests).
- `Actor::Schedule` with a name label in the action record; a nullable agent in notifications.
- Scheduled entry points in hierarchy (hold guard, queue) and agent (wake actor), and the scheduler and run executor in the host.
- Schedule cap setting; the Schedules dialog; mock core, unit, wire, and e2e tests; living-spec merge notes.

**Why this approach:**
- The server runs while the desktop app is closed (0001/FR-019), so the server owns timers and schedules.
- Run steps reuse the code that the person's wake and an agent's directive run, so the queue, the question check, and the 0013 watch stay one implementation. A schedule is not an agent, so the three agent-bound checks (sender in the tree, per-sender rate limits, automatic hold) get a scheduled variant instead of a fake sender.
- Modules may not depend on each other (`scripts/check-boundaries.sh`). `schedule` depends on the kernel only; the host (`bridges`) joins it to hierarchy, agent, and notification, as `TempEnder` already does.

**What it will not do:** the spec's Out of scope list.

**Shape of the work:** 6 tasks, one PR (`feat/0025-scheduled-directives`), one commit per task. **Effort:** XL.

## Goal

Every FR and SC of `specs/changes/0025-scheduled-directives/SPEC.md`, proven by unit, wire, and e2e tests, with CI green on Linux, macOS, and Windows.

## Decisions

- **D1 Time zone and DST.** The schedule domain depends on `jiff` (exact version `=0.2.45`, the locked one, added to `[workspace.dependencies]`; default features so the zone database is bundled on Windows). A zone comes from a `ZoneSource` trait (`fn current() -> TimeZone`), so tests pass a fixed zone and a zone that changes. A once, daily, or weekly due time is `civil date + time` resolved in the zone with `jiff`'s `Disambiguation::Compatible` (a skipped time becomes the first minute after the gap, a repeated time takes its first occurrence), which is what FR-004 says. An every-N-hours due time is `anchor_ms + k * N * 3_600_000` with `k >= 1`; no zone is involved. The scheduler re-reads the zone each round and recomputes `next_due` when its identifier changed (FR-004, 60 s bound met by the 5 s tick). Whether `jiff` re-reads the system zone at run time is checked in T1 (R1); the zone-change test uses the `ZoneSource` fake.
- **D2 Next due and handled due.** `Schedule { next_due: Option<Timestamp>, last_handled_due: Option<Timestamp>, anchor: Timestamp, ... }`. `next_due(now)` is the first due time later than both `now` and `last_handled_due` (FR-003). `last_handled_due` is the largest due time with a recorded result, so a clock set back cannot repeat a run (FR-005, SC-006).
- **D3 Round rule.** One round, for each schedule that is on: list its due times `d` with `last_handled_due < d <= now` (a bounded loop; at most 200 000 steps per round so a 100-year jump cannot hang; the rest is counted in one batch by arithmetic for every-N-hours and by day stepping for the others, T1 detail). Each `d` with `now - d <= GRACE` (120 s) is a run; each older `d` joins one missed batch (count, first, last). The server's earlier absence needs no heartbeat: every due time not yet handled and older than the grace is missed, which covers a stop, a machine sleep, and a forward clock jump (FR-005, FR-006). A new schedule, an edit, and a switch on set `last_handled_due = max(last_handled_due, now)` so nothing before that moment is ever missed or run (FR-003, FR-014: no run for the time it was off).
- **D4 Run state.** A run is a row in `schedule_runs` (`id`, `schedule_id`, `due`, `started`, `via` `due|now`, `result` NULL while open, `reason`, `queue_entry` NULL or the id of the waiting directive). An open run (`result` NULL) or a run whose result is `waiting` makes the next run `skipped: previous run still waiting` (FR-008). At server start every open run and every run whose result is `waiting` becomes `failed: the server stopped` (edge case; the queue is gone and nothing is started). A result is written by one conditional UPDATE (an open run takes any result, a waiting run takes `submitted`, `unsubmitted`, or `withdrawn`), so two writers never overwrite each other. Only the last 20 settled rows per schedule are kept: the delete of older rows, in the same transaction as the insert, never removes an open or waiting row.
- **D5 Missed entries.** A missed batch is one history row with `result = missed`, `reason` = "N runs missed, first <local>, last <local>", plus one action record entry (actor Schedule, in the target's record) with the same text, and `last_missed` on the schedule. One notification per minute (FR-006, owner decision): the scheduler keeps the last minute for which it notified and, when a round adds missed entries in that same minute, it adds the count to that notification (update of the row's text and the number of schedules) instead of a second row. A once schedule in a missed batch is switched off with the off reason `missed`.
- **D6 Actor.** `kernel::Actor::Schedule(ScheduleId)` with `ScheduleId` (a UUID, like `AgentId`) in the kernel. Text form `schedule:<uuid>` in the audit codec (both copies; a test pins the two together). The serde tag `kind` and content key `agent_id` stay unchanged (review L3: no key rename, so no stored JSON can stop parsing); the content of the new variant is the schedule id under the same key, and a serde round-trip test of all four variants pins it.
- **D7 Actor label.** The action record must show the schedule's name and the note that the person made it, also after a rename or a delete. `ActorScope::enter_labeled(actor, label)` keeps an optional label beside the actor (thread-local `RefCell<Option<Arc<str>>>`; `enter` clears it). `ActionJournal` writes it to a new nullable audit column `actor_label` (migration `0004_actor_label.sql`), and the audit presentation shows `"<label> (schedule <id8>, made by the person)"`. The scheduler enters every run with the label of the schedule's name at that moment.
- **D8 Settings.** `SettingKey::ScheduleCap` (`schedule_cap`, default 50, 1 to 200, refusal text names the range and keeps the stored value). The save checks the count of schedules (on and off) against it inside the store transaction (no race with a second window).
- **D9 Hold guard for a schedule.** `HoldService::guard_scheduled(action, target, rows)` in hierarchy: refuses when the office is on hold or an agent hold covers the target (its own hold or an ancestor's, as 0007/FR-004), with the 0007 reason texts; for a directive it also checks the "directives sent to one target agent" limit against the **schedule window**, a separate count in the rate windows (`rate_windows.rs`) keyed by target that only scheduled directives write and read, with the same limit value as the agents' window; a scheduled directive never adds to the agents' window, so a schedule can never make an agent's directive refused (review L2, FR-007, PB-4, SC-008). It never counts a refusal toward `auto_hold` and never starts an automatic hold or a notification (A4). It is called twice, at the run start and again right before the queue push (FR-007, SC-007).
- **D10 Scheduled directive.** The sender is the schedule (review M1). `WaitingDirective` gets `sender: Sender` = `Agent(AgentId) | Schedule(ScheduleId)` (or `Option<AgentId>` plus the origin; T3 picks the smaller diff), and T3 first lists every read of `WaitingDirective.sender` (recheck, journal, the 0011 task line, the 0007 counters, the report/objective code, idle-sleep blocking, the desktop-facing queue view) and gives each a scheduled branch; no read may see the target as the sender. `SendDirectiveHandler::queue_scheduled(ScheduledDirective { schedule: ScheduleId, target, text, run_id })` checks text rules (`validate_directive_text`), queue full (`refused`), `guard_scheduled`, then pushes the entry with `origin = Origin::Scheduled { run_id }` and returns the place or `submitted`; a not running target is the caller's `skipped` decision before the call. `recheck` does not withdraw a `Scheduled` entry for a changed tree (A11); the stop, hold, timeout, and server-stop withdrawals of 0012/FR-005 stay. Records (modified 0012/FR-003 and FR-005): an unsubmitted result and a withdrawal of a scheduled entry are written once, in the target's record only, with the schedule as actor (no sender record exists); the journal gets `record_scheduled`. Settle: the queue reports `submitted`, `unsubmitted`, or `withdrawn(reason)` of an `Origin::Scheduled` entry through a new port `ScheduledOutcomes::settled(run_id, outcome)`, which the host implements by updating the run row and, for a failure kind, notifying (FR-009, FR-011). The task line (0011) is fed as for any submitted directive (A11).
- **D11 Wake.** `ResumeContext::wake` takes the actor (`User` for the person, `Schedule` for a run) instead of the literal at `:258`, and gets `wake_and_wait(agent_id, actor) -> WakeResult` that waits for the 0013 watch result (`continued`, `new session`, `on hold`, `failed`). The sign-in check, the fallback, and the hold stay as they are; the wake entry has the schedule as actor through `ActorScope`. A target that is `going to sleep` makes the run wait (polled by the round, at most the 10-minute directive limit, then `failed: still going to sleep`) and then wake (FR-010). A wake that did not end when the server stops makes the run `failed: the server stopped` (open-run rule of D4).
- **D12 Scheduled temp: out of this change.** Split off by the review (spec Out of scope). The follow-up change adds a temp action to a schedule and reuses the scheduler, `Actor::Schedule`, the label, and the notification. Nothing in this plan builds it.
- **D13 Target gone.** When an agent is removed (delete, subtree delete, the end of a temp), `AgentGateway::run` calls `ScheduleBridge::agents_removed(ids)` after the success; the bridge switches every schedule whose target is in `ids` off with the off reason, records it, and notifies once (FR-010, SC-011, 2 s bound). The round also re-checks existence of each target before a run, so a missed hook cannot run against a missing agent.
- **D14 Notifications.** `Notification.agent_id` becomes `Option<AgentId>` and `agent_name` keeps a display text: a schedule notification names the schedule and carries the target's id when it has one; the "missed runs" notification has none. Migration `0006_notification_agent_optional.sql` rebuilds the table (SQLite cannot drop NOT NULL). New `NotificationEvent::Schedule` (and a `detail` text). The one-per-schedule-until-success rule is the schedule's flag `notified_since_success` (set on a notifying result, cleared on a successful run) (FR-011). Needs you is not touched (A6). The desktop notification list shows a row without an agent as plain text with no jump action.
- **D15 Agent refusal.** An agent connection request whose kind starts with `schedule.` is refused with the reason "only the person makes schedules" and recorded as 0002/FR-009 requires (FR-014). The agent allowlist (`H/server/agent_call.rs`) gets no schedule kind, so a test asserts the refusal for each of the 5 kinds (SC-016).
- **D16 Wire.** User requests: `schedule.list`, `schedule.save` (create when no id, edit with an id), `schedule.switch` (`on`), `schedule.run_now`, `schedule.delete`, `schedule.history`. Errors use the existing codes (`invalid` with a `fields` array of field and rule; `refused` for the cap and a switch on that the rules refuse; `not_found`). Events: `schedule.changed` (the whole row), `schedule.removed` (id). Field limits are checked on the server; the desktop checks the same rules for a quick message and the server decides (as 0018 does).
- **D17 Scheduler task.** `Scheduler` in `H/server/schedule_run.rs`, shaped like `TempWatcher`: `interval(5 s)`, `MissedTickBehavior::Delay`, `spawn_blocking(round)`. It waits for `SweepGate::wait_until_done` before the first round and skips a round while the sweep runs again (FR-005). Each run is its own `tokio::spawn`ed job (a wake waits up to the check period), with a per-schedule guard so a run of one schedule never starts twice (D4). Server stop: the task stops on the shutdown token; open runs are failed at the next start (D4); a waiting directive is withdrawn by 0012 on a normal stop. A run job never starts before the round that found it commits `last_handled_due`, so a crash cannot repeat it.
- **D18 Run now.** `schedule.run_now` makes one run with `via = now`, with the same guards (D9, D4), and changes neither `next_due`, `last_handled_due`, `anchor`, nor the switch (A13). It works for a schedule that is off, and is refused for a schedule with an off reason `target deleted` (its target is gone).
- **D19 Desktop.** A new `D/modules/schedule/` (models, service, controller, `schedules-dialog.svelte`, `schedule-form.svelte`, `schedule-history.svelte`) built from the existing dialog, list, form, and `confirm-dialog.svelte`; a "Schedules" entry beside "Temps" with its keyboard shortcut registered where the Temps one is; the limits dialog gets the schedule cap field; the agent details and the action record view show the actor label. No new visual style (spec: Design). The weekly day check boxes are separate labelled controls; the row has the accessible name and description the spec sets.
- **D20 Local time in the view.** The server sends due times as unix millis plus the zone identifier; the desktop formats with `Intl.DateTimeFormat` in the machine's zone, with the weekday and date. The weekly and daily time fields are `HH:MM` text, sent as such.

## Risks

- **R1 Zone change detection.** `jiff` may cache the system zone. T1 proves detection with the `ZoneSource` fake, then checks `jiff`'s system behavior on Linux; if it caches, the production `ZoneSource` re-reads `TZ` and `/etc/localtime` each round on Unix. A platform that cannot be proven is recorded in the qa report, never claimed as passed.
- **R2 Notification migration and merge order.** The merge order of the open changes is 0024, 0026, then this one: at merge, renumber the migrations (audit `0004`, notification `0006`, schedule `0001`) and the enum counts (`NotificationEvent`, `ALL` arrays) on top of main.  A table rebuild touches a shipped table. Mitigation: a migration test with rows of every event kind, and a copy-then-swap in one transaction.
- **R3 Actor change reach.** About 43 files match on `Actor`. Mitigation: T1 lands first and the compiler finds each match; the codec has a round-trip test.
- **R4 Wake waits.** A wake waits up to the check period; many schedules due together must not block the round. Mitigation: runs are separate jobs (D17) and SC-015 (50 runs in 60 s) is a test.
- **R5 Size.** The change is still over the spec contract's size rule after the temp split (14 FR). The review accepted the directive schedule as one change; tasks are one commit each, so a further split stays possible.
- **R6 Removal hook coverage.** A removal path that skips `AgentGateway::run` would not switch a schedule off at once. Mitigation: the pre-run existence check of D13 and a test per removal path (delete, subtree delete, the end of a temp agent that is a target).

## Result

T1 to T6 are done. The code gate (r3) found one high and six medium findings and eight low ones; the fixes are in the commits after the merge of 0026: a waiting run is failed at a start (H1), a due time before the start is missed (M1), an unreadable tree fails the run before a wake (M2), a round saves each schedule before it launches its runs and reports storage failures (M3), a second wake of the same target queues (M4), a result is one conditional UPDATE (M5), and the lows L1 to L7.
