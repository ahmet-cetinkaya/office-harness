# Research: 0003 panel practicality

Date: 2026-11-17. Verified against the 0001 sources on `main` (merge `7750602`) and the crate sources in the local Cargo registry.

## R1: Do `Ctrl+Shift+F1` to `Ctrl+Shift+F10` reach the app on every webview and OS?

**Question:** does a page-level key handler see the agent and switcher shortcuts (FR-004, D8), or does the webview, the desktop environment, or the OS take the key first?

**Findings:**

- **Linux (WebKitGTK through wry).** WebKitGTK ships no built-in browser shortcuts of its own: the wry tracker records that page reload (`Ctrl+R`, `F5`) and DevTools (`Ctrl+Shift+I`, `F12`) do nothing unless the embedding application implements them (`https://github.com/tauri-apps/wry/issues/345`). GTK dispatches window accelerators in the capture phase before the focused widget, so an application accelerator could take a key first (`https://docs.gtk.org/gtk4/input-handling.html`), but the office app installs no GTK accelerators; a Tauri issue contrasts this with the CEF backend, where the same combos never reach the renderer, and states that the wry/WebKitGTK runtime delivers the keydown to the page (`https://github.com/tauri-apps/tauri/issues/16249`). Two WebKitGTK quirks matter for the handler: report the key by `event.code`, because at least one `Ctrl+Shift+` combo arrives with `event.key` set to `Unidentified`, and give the webview keyboard focus, because with no key-focused widget WebKitGTK dispatches no keydown at all.
- **KDE Plasma.** The Plasma defaults take plain `Ctrl+F1` to `Ctrl+F4` (virtual desktops), `Ctrl+F7`, `Ctrl+F9`, `Ctrl+F10` (present windows), and `Ctrl+F12` (show desktop) globally (`https://docs.kde.org/stable_kf6/en/khelpcenter/fundamentals/kbd.html`). None of the primary Plasma documentation binds `Ctrl+Shift+F1` to `Ctrl+Shift+F12`. A secondary source, the Krusader key-binding page, lists `Ctrl+Shift+F1..F12` under "General Ctrl keys" as "Standard (Plasma) key-bindings" (`https://docs.kde.org/trunk_kf6/en/krusader/krusader/key_bindings.html`), which suggests that Plasma names the family somewhere, without naming an action. The evidence that the keys are free is therefore one-sided but consistent; the QA report keeps a hands-on row for KDE.
- **GNOME.** The GNOME keyboard-shortcut settings page binds no `Ctrl+Shift+F` combination and no bare F-key in the F1 to F12 range by default; workspaces use Super-based combinations, and the F-key bindings it lists are `Alt+F2`, `Alt+F4`, `Alt+F6`, `Alt+F7`, `Alt+F8`, `Alt+F10` (`https://help.gnome.org/users/gnome-help/stable/keyboard-shortcuts-set.html.en`).
- **Windows (WebView2 through wry).** No `Ctrl+Shift+F1` to `Ctrl+Shift+F10` combination is reserved by the OS; the documented reserved keys are `Ctrl+Alt+Del` and `Win+L`, and the PowerToys Keyboard Manager documentation confirms F-keys themselves are remappable, so they are not system-owned (`https://learn.microsoft.com/en-us/windows/powertoys/keyboard-manager`). WebView2 keeps a set of browser accelerator keys, documented on `ICoreWebView2Settings3.AreBrowserAcceleratorKeysEnabled`: find, print, reload, zoom, and DevTools (`Ctrl+Shift+I`, `F12`); none of them is an F1 to F10 combination, and the setting can turn the whole set off (`https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2settings3`). wry already wraps this switch, but Tauri does not expose it on the window builder (`https://github.com/tauri-apps/tauri/issues/16306`), so the default stays on. Side note for the QA report: the existing focus shortcut `Ctrl+Shift+F12` (0001 A12) is not in the documented WebView2 accelerator list either, but a hands-on row on Windows should confirm it.
- **macOS (WKWebView through wry).** This is the one real conflict. By default the top-row keys of an Apple keyboard are media and brightness keys, and macOS consumes them before any application sees a key event; the F-key reaches the app only when the user holds Fn (or Globe), or turns on "Use F1, F2, etc. keys as standard function keys" in System Settings (`https://support.apple.com/en-us/102439`). Apple documents no modifier combination that turns a media key back into an F-key; the Fn key and, on keyboards without Fn, the Control key are the only documented substitutes. Holding `Ctrl+Shift` while pressing a media-key-mapped F1 is therefore not guaranteed to deliver an F1 keydown. When the F-key does reach the app (Fn held, or standard function keys on), no macOS default binding takes `Ctrl+Shift+F1` to `F10`: the historical Exposé bindings on F9 to F11 are gone from current macOS, and current defaults map the top row to media controls only.

**Fallback table (recorded, not yet applied):**

| Default | Where it fails | Fallback |
|---|---|---|
| `Ctrl+Shift+F1` to `Ctrl+Shift+F9` | macOS in default media-key mode, unless Fn is held | Keep the key and document Fn (the Clarifications already expect this), or switch the macOS build to `Cmd+Alt+1` to `Cmd+Alt+9`, which no webview or macOS default takes |
| `Ctrl+Shift+F10` | same as above | `Cmd+Alt+0` on macOS |
| `Ctrl+Shift+F1` to `Ctrl+Shift+F10` | KDE, if a distribution binds the Plasma "standard" family globally | `Cmd`/`Ctrl+Alt+1..9,0` family; one table entry per key, so a per-OS build change is small |

The shortcuts live in one key-binding table (D8), so any of these changes is a table edit plus a README edit.

**Decision:** keep `Ctrl+Shift+F1` to `Ctrl+Shift+F10` as the defaults on all three OSes, document the macOS Fn requirement, and keep the fallback table above for the QA pass to trigger. The hands-on rows for KDE and macOS go into the QA report (T9). Verified 2026-11-17, sources `https://github.com/tauri-apps/wry/issues/345`, `https://docs.gtk.org/gtk4/input-handling.html`, `https://github.com/tauri-apps/tauri/issues/16249`, `https://docs.kde.org/stable_kf6/en/khelpcenter/fundamentals/kbd.html`, `https://docs.kde.org/trunk_kf6/en/krusader/krusader/key_bindings.html`, `https://help.gnome.org/users/gnome-help/stable/keyboard-shortcuts-set.html.en`, `https://learn.microsoft.com/en-us/windows/powertoys/keyboard-manager`, `https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2settings3`, `https://github.com/tauri-apps/tauri/issues/16306`, `https://support.apple.com/en-us/102439`.

**Spec note:** the Clarifications entry of 2026-11-17 already says the F-keys may need Fn on macOS. R1 sharpens it into a guarantee (Fn or the system setting is required, not "on most keyboards") and adds the KDE caveat. The spec's Clarifications entry needs a small amendment to that effect; the spec is not edited here.

## R2: The Tauri notification plugin for v2

**Question:** which crate and npm versions, how does the permission flow work, can a click select an agent on each OS, and what does Linux need at build and run time (D7)?

**Findings:**

- **Versions.** The Rust crate is `tauri-plugin-notification`, latest stable 2.8.1, published 2026-11-10 (`https://crates.io/api/v1/crates/tauri-plugin-notification`). The npm package is `@tauri-apps/plugin-notification`; the JavaScript package is released in lockstep with the crate in the plugins workspace, and the matching release is `notification-js` 2.8.1 (`https://github.com/tauri-apps/plugins-workspace/releases/tag/notification-v2.8.1`). The plugin needs Rust 1.90 or newer (`https://v2.tauri.app/plugin/notification/`), which the workspace toolchain 1.100 satisfies. The workspace pins exact versions, so the manifest lines are `tauri-plugin-notification = "=2.8.1"` and `"@tauri-apps/plugin-notification": "2.8.1"`.
- **Permission flow.** The webview calls `isPermissionGranted()` and, when it is false, `requestPermission()`, which resolves to `'granted'` or `'denied'`; only then does `sendNotification({ title, body })` show anything (`https://v2.tauri.app/plugin/notification/`). The commands the webview may call are granted through the capability file with `notification:default` (`https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/fr/plugin/notification.mdx`). T7 must confirm at build time that `notification:default` includes the send permission (`allow-notify`) and add it explicitly if it does not.
- **Click handling.** The JavaScript API has `onAction(cb)`, and the reference states that on desktop it is emitted when the user clicks a notification, with `actionId` set to `"tap"`, for notifications shown while a listener existed (`https://v2.tauri.app/reference/javascript/notification/`). Platform caveats from the same page: on Windows the click is reported only while the toast is on screen, not after it moves to the Action Center; on macOS two or more actions collapse into an "Options" menu; on Linux the report depends on the notification server delivering the action signal. Desktop action reporting arrived in plugin 2.6.0, and 2.7.0 fixed notifications closing immediately on GNOME (`https://github.com/tauri-apps/plugins-workspace/releases/tag/notification-v2.6.0`). The handler runs in the webview, so opening the agent means calling the same code path as a row click; bringing an unfocused window to the front needs the Tauri window API in the same handler.
- **Linux dependency.** On Linux and the BSDs the plugin pulls `notify-rust` (^4.18) and `zbus` (^5) (`https://crates.io/api/v1/crates/tauri-plugin-notification/2.8.1/dependencies`). `notify-rust`'s default backend is the pure Rust `zbus` client, which needs neither `libdbus` nor `libnotify`; the `dbus` crate backend that links the C library is opt-in behind a feature (`https://docs.rs/notify-rust/latest/notify_rust/`, `https://lib.rs/crates/notify-rust`). So the CI desktop build on Linux needs no `apt install` step for notifications; at run time a D-Bus session must exist, which every desktop session provides. Headless CI cannot show notifications, so real OS delivery stays a hands-on QA row on all three OSes.

**Decision:** pin `tauri-plugin-notification = "=2.8.1"` and `@tauri-apps/plugin-notification = "2.8.1"` (T7), request permission once at first use, fall back to the in-panel list on `'denied'`, select the agent from the `onAction` handler with `actionId === "tap"`, and add no Linux CI package. Verified 2026-11-17, sources listed above.

## R3: Bell detection through the parser the terminal module uses

**Question:** does the parser that `screen_emulator.rs` already runs report a `0x07` outside an OSC string as a bell, and not inside one (D3)?

**Findings:** the terminal module parses output with `vt100` 0.18.1 (`vt100 = "=0.18.1"` in the root `Cargo.toml`; `src/modules/terminal/infrastructure/src/services/screen_emulator.rs` holds one `vt100::Parser`), which delegates the state machine to `vte` 0.15.0.

- The `vte` parser enters `State::OscString` on `ESC ]` and, inside that state, a `0x07` byte ends the string: `0x07 => { self.osc_end(performer, byte); self.state = State::Ground }`, with no call to `performer.execute` (`vte` 0.15.0, `https://docs.rs/crate/vte/0.15.0/source/src/lib.rs`, `advance_osc_string`). So a `0x07` that terminates a window-title sequence is part of the sequence, not a bell.
- Outside an OSC string, `0x07` reaches `Perform::execute`, which `vt100` maps to the bell callback: `7 => self.callbacks.audible_bell(&mut self.screen)` (`vt100` 0.18.1, `https://docs.rs/crate/vt100/0.18.1/source/src/perform.rs`, `execute`). The same file maps `ESC g` to `visual_bell`, which the office does not use; the audible bell is the one the CLI CLIs send.
- The callback is a trait on the parser's type parameter: `Parser<CB: Callbacks>`, built with `Parser::new_with_callbacks(rows, cols, scrollback, callbacks)`, and readable afterwards through `parser.callbacks()` (`vt100` 0.18.1, `https://docs.rs/crate/vt100/0.18.1/source/src/parser.rs` and `https://docs.rs/crate/vt100/0.18.1/source/src/callbacks.rs`). Today `ScreenEmulator::new` calls `Parser::new`, which uses the unit type `()` and drops the event.

**Decision:** `ScreenEmulator` builds its parser with a small bell collector that implements `vt100::Callbacks::audible_bell`, counts the bells, and exposes `take_bells()`, which returns and clears the count since the last call. The session turns each counted bell into one `TerminalEvent::Bell`. This reads the parser state, so the OSC-window-title `0x07` never becomes a bell, and a bell split across reads is held by the state machine until the string ends. Verified 2026-11-17, sources `vte` 0.15.0 (`https://docs.rs/crate/vte/0.15.0/source/src/lib.rs`) and `vt100` 0.18.1 (`https://docs.rs/crate/vt100/0.18.1/source/src/perform.rs`, `https://docs.rs/crate/vt100/0.18.1/source/src/callbacks.rs`, `https://docs.rs/crate/vt100/0.18.1/source/src/parser.rs`).

**CI evidence for the bell behavior** (2026-11-18):

- **ConPTY stalls all child output until the master answers its `ESC[6n` handshake.** ConPTY's first bytes ask for the cursor position; until the master replies, no child output reaches the master read. The runs [`44193788447`](https://github.com/ahmet-cetinkaya/office-harness/actions/runs/44193788447) and [`44195294535`](https://github.com/ahmet-cetinkaya/office-harness/actions/runs/44195294535) show the fixture children producing nothing before the answer existed. The product answers now: `ScreenEmulator::process` replies to each `ESC[6n` it parses (`terminal_query.rs`).
- **conhost's own title `BEL` reaches the master stream and the parser counts it as no bell.** ConPTY emits its window-title OSC `ESC]0;...exe BEL` with a `0x07` terminator; the master read forwards it verbatim, and the `vte` state machine counts zero bells for it. The tap of run [`44209136803`](https://github.com/ahmet-cetinkaya/office-harness/actions/runs/44209136803) shows the byte in the hexdump and `0x07 occurrences in master stream: 1` with no `Bell` event on any OS.
- **The Windows stall was in the test fixture, not the product.** Run [`44212610497`](https://github.com/ahmet-cetinkaya/office-harness/actions/runs/44212610497) tapped the bell test: the master stream held conhost's title and the echoed input `a`, `ab` only — the child never wrote its bell section. The fixture's `enter_raw_mode` was a Unix-only no-op; a pseudoconsole console starts in line-input mode, so the child's per-byte `read` waited for a line break that never came. The fix clears `ENABLE_LINE_INPUT`, `ENABLE_ECHO_INPUT`, and `ENABLE_PROCESSED_INPUT` through `console-control` (`windows-sys` 0.61.2, `https://docs.rs/crate/windows-sys/0.61.2/source/src/Windows/Win32/System/Console/mod.rs`), the same modes `stty raw -echo` clears on Unix.

## R4: The last non-empty screen line with the same parser

**Question:** can the tracker read the last non-empty line from the parsed screen, correctly across carriage-return redraws, wrapped lines, and the alternate screen (D2)?

**Findings:**

- `vt100::Screen::contents()` returns the screen as plain text with no formatting information (`vt100` 0.18.1, `https://docs.rs/crate/vt100/0.18.1/source/src/screen.rs`, `contents`). The grid writer joins rows with `\n` but skips the line break on a row that the previous row wrapped into, so one logical line that spans two screen rows stays one `\n`-free run (`https://docs.rs/crate/vt100/0.18.1/source/src/grid.rs`, `write_contents`). Trailing line breaks are trimmed. Splitting `contents()` on `\n` and taking the last segment that is not whitespace gives the last visible line, wrapped lines included.
- Carriage-return redraws are applied by the parser itself: `\r` moves the cursor to the column origin and later cells overwrite the row in place (`https://docs.rs/crate/vt100/0.18.1/source/src/perform.rs`, `execute`: `13 => self.cr()`). The row text after `0%\r50%\r100%` is `100%`; no scan of the raw byte stream is involved.
- The alternate screen of a full-screen CLI lives in its own grid: `Screen::alternate_screen()` reports it and the internal `grid()` accessor returns the alternate grid while it is active (`https://docs.rs/crate/vt100/0.18.1/source/src/screen.rs`). `contents()` therefore reads the TUI's screen while it runs, and the main screen again after it leaves. This is exactly what the desktop's own snapshot does (`screen_emulator.rs`, `snapshot`).

**Recorded fixtures for T2** (fed to `ScreenEmulator::process` on an 80-column screen unless said otherwise; expected result of the last-line read):

| Bytes | Last line |
|---|---|
| `b"first\r\nsecond\r\n"` | `second` |
| `b"\x1b[31mred\x1b[0m plain\r\n"` | `red plain` (no color codes) |
| `b"0%\r50%\r100%\r\n"` | `100%` (carriage-return redraw) |
| `b"0123456789ABCDEFGHIJ\r\n"` on a 10-column screen | `0123456789ABCDEFGHIJ` (wrapped row joins back into one line) |
| `b"main line\r\n\x1b[?1049h\x1b[2J\x1b[1;1Hprogress: 40%"` | `progress: 40%`; after `b"\x1b[?1049l"` it is `main line` again |
| `b"\r\n\r\n"` | none (blank screen, the spec's "no output yet" edge case) |
| `b"ready\x07"` | line `ready`, one bell (R3) |
| `b"\x1b]2;window title\x07after\x07"` | line `after`, one bell (the title's `0x07` is no bell) |

**Decision:** the tracker asks the emulator for `contents()`-derived last line on every output burst, cuts it to 200 characters, keeps it for the agent snapshot, and publishes a change event at most once per second. A line longer than 200 characters is cut on the server (D2); the full text stays in the terminal. Verified 2026-11-17, sources `vt100` 0.18.1 (`https://docs.rs/crate/vt100/0.18.1/source/src/screen.rs`, `https://docs.rs/crate/vt100/0.18.1/source/src/grid.rs`, `https://docs.rs/crate/vt100/0.18.1/source/src/perform.rs`).

## R5: ARIA and focus patterns for the switcher dialog and the live region

**Question:** which dialog and live-region patterns do the switcher and the notification announcements follow (D11)?

**Findings:**

- **Dialog (WAI-ARIA Authoring Practices, Dialog Modal pattern, `https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/`).** On open, focus moves to the first focusable element, or to a static element with `tabindex="-1"` when the content is structured, as the switcher's filter field and result list are. Tab and Shift+Tab cycle inside the dialog and wrap at its ends; the dialog offers no way to move focus outside without closing. Escape closes it. On close, focus returns to the invoking element, or to another element that fits the workflow when the invoker is gone. The container has `role="dialog"`, is named by `aria-labelledby` pointing at a visible title, and sets `aria-modal="true"` only when the app blocks interaction outside and the styling obscures it; the switcher blocks the panel behind it, so it sets it.
- **Live region (MDN, ARIA Live Regions, `https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/ARIA_Live_Regions`).** Announce new notifications with `role="status"` (implicitly `aria-live="polite"`; the page recommends adding the explicit attribute for compatibility), not `assertive`, because a notification is important but interruptible. `aria-atomic="true"` makes the whole message read as one sentence, which a notification text needs. The region must exist in the initial markup, empty, before any update arrives; regions created in JavaScript are announced unreliably. Keep the message short, plain text, and keep urgent error messages in a separate `role="alert"` region instead of mixing priorities in one region.
- The 0001 webview runs Playwright with `@axe-core/playwright` (`src/apps/desktop/e2e/office.spec.ts`), so the dialog and the live region are covered by the same harness at the two widths the plan fixes.

**Decision:** the switcher is a `role="dialog"` with `aria-modal="true"`, named by its visible title, focus placed in the filter field on open, a Tab cycle inside, Escape returning focus to the invoker. New notifications are announced by one `role="status"` `aria-live="polite"` `aria-atomic="true"` region present from the first render. Verified 2026-11-17, sources `https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/`, `https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/ARIA_Live_Regions`.
