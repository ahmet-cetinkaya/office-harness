## R1: The merged 0003 last-view code, and the `view` extension of D6

**Question:** what is the exact `last_view` shape, validator, and write throttle on `main`, and can the validator take the added `view` field (D6, the rollback condition)?

**Findings (all on `main` today):**

- **Setting key and storage.** `last_view` is one key of `SettingKey` in `src/modules/agent/domain/src/value_objects/settings.rs` (`SettingKey::LastView`, `as_str()` returns `"last_view"`; `SettingKey::ALL` has five keys). The value is one row of the 0001 `agent_settings` key-value table; no new table and no migration. `Settings::default()` sets `last_view: None`; `value_of(SettingKey::LastView)` returns the empty text when no view is stored, so `settings.get` answers `{"key": "last_view", "value": ""}`.
- **Validator** (`parse_last_view` in the same file, reached through `Settings::set_from_text`, called by `SetSettingHandler::handle` in `src/modules/agent/application/src/commands/set_setting/set_setting_handler.rs`):
  - Empty text clears the stored view (becomes `None`).
  - Longer than `LAST_VIEW_MAX_BYTES = 1_024` bytes of raw UTF-8 (`text.len()`) is refused: `AgentError::TooLarge { field: "last_view", max: 1_024 }`.
  - Not valid JSON, not an object, or missing one of the three documented keys is refused: `AgentError::InvalidLastView`. The shape check is `holds_the_documented_shape`: an object whose `project` and `agent` are a string or null and whose `terminal_open` is a boolean.
  - **Unknown keys are ignored.** The check reads only the three documented keys and says so in its doc comment ("Unknown keys are ignored, so a client may store more and a later change may add keys"). The test `a_last_view_may_carry_keys_that_a_later_change_adds` (`src/modules/agent/domain/src/value_objects/settings.tests.rs`) pins it with exactly the 0005 case: `{"project": null, "agent": null, "terminal_open": false, "view": "scene"}` stores and reads back unchanged. The rollback condition of the plan holds: a value written after this change restores on an app built before it.
  - Both refusals surface on the wire as code `invalid` naming the field: `AgentError` maps to `ApplicationError::Invalid` in `src/modules/agent/application/src/common/errors/application_error.rs` (only `ReservedShortcut` maps to `Conflict`), and `HandlerError::from` maps `Invalid` to `ErrorCode::Invalid` in `src/modules/agent/presentation/src/handlers/handler_error.rs`. This matches the 0003 contract wording.
- **The D6 extension, exact key order and size impact.** The documented key order is `project`, `agent`, `terminal_open` (0003 data model and contract; the tests write it in that order). 0005 appends `view` last, so a write is `{"project": <id or null>, "agent": <id or null>, "terminal_open": <bool>, "view": "panel" | "scene"}`. Adding the field costs 15 to 17 bytes per write (`, "view":"panel"` compact, more with spaces), against an unchanged 1 KiB cap; the project and agent id lengths dominate, and an over-cap value is refused exactly as before, so no validator change is needed for 0005. An unknown or missing `view` restores the panel (D6), which the client reads, not the server: the server stores and returns the text unchanged (`settings.get` returns the stored text unchanged, 0003 contract, and the validator never strips keys).
- **Write throttle.** The contract (0003 `specs/changes/0003-panel-practicality/contracts/panel-protocol.md`, "Changed setting") and data model say the desktop writes `last_view` at most once per second and on close. The writer is desktop code and does not exist on `main` yet. **Pending 0003 desktop merge — re-verify before T2/T3 build:** the writer file (0005 plan names `M/panel/state/`), its throttle, and the restore-on-start read. The server accepts a write from any client at any rate; nothing on the server side throttles.
- **Tests on `main` that hold the behavior:** `a_last_view_of_the_documented_shape_stores_and_reads_back`, `an_empty_last_view_clears_the_stored_view`, `a_last_view_past_one_kib_is_refused`, `a_last_view_that_is_not_the_documented_shape_is_refused`, `a_last_view_may_carry_keys_that_a_later_change_adds` (all in `settings.tests.rs`), the round trip in `set_setting_handler.tests.rs`, and over the wire `the_last_view_is_stored_and_read_back` and `a_last_view_that_is_oversize_or_not_the_shape_is_refused` (`src/apps/office-harnessd/tests/agent_protocol.rs`).

## R2: The merged 0003 panel pieces

**Question:** which of the panel pieces that the scene reuses (project switcher component, its name match function, the `TerminalView` embed, the focus-leave shortcut) exist on `main`?

**Findings:**

- **What exists on `main` (`4195167`):** there is no `src/apps/desktop/src/modules/panel/` folder. The module list is `access`, `agent`, `audit`, `hierarchy`, `terminal`. No project switcher component, no switcher dialog, no name match function, no last-view writer exist anywhere in the webview today: the only name filtering in the webview is `ACTIVE_STATUSES.includes(status)` in `modules/agent/models/agent.ts`, which is not a name match.
- **What the terminal embed looks like today (reusable as D5 needs):** `modules/terminal/index.ts` exports exactly one symbol, `export { default as TerminalView } from "./views/terminal-view.svelte"`. Its props are `client: CoreClient`, `agentId: string`, `agentName: string`, `isRunning: boolean` (`interface Props` in `views/terminal-view.svelte`). The office view embeds it in `modules/agent/components/agent-details.svelte` (`<TerminalView {client} agentId={agent.id} agentName={agent.name} {isRunning} />`, wrapped in `{#key isRunning}`), which is the in-place embed, no second window, that D5 copies. A non-running agent's terminal shows the last session's output with `disableStdin` (`isRunning` false), which serves the D5 stopped-desk behavior.
- **The focus-leave mechanism that exists today:** the terminal itself owns the way out. `views/terminal-view.svelte` loads the shortcut with `loadFocusShortcut(client)` (`modules/terminal/services/focus-shortcut.ts`, reads `settings.get` with key `focus_shortcut`, falls back to `DEFAULT_FOCUS_SHORTCUT` = `"Ctrl+Shift+F12"` from `core/shortcuts`), matches keys with `matchesShortcut(shortcut, event)` (`core/shortcuts/shortcut.ts`, exact modifiers and key), and calls `heading.focus()` on its own `<h3>`. So on `main`, focus leaves the terminal to the terminal's own heading, not to a panel; a panel that receives focus does not exist yet.
- **What the 0003 plan promised (from `specs/changes/0005-office-scene/PLAN.md` Context, which records the 0003 draft):** a `modules/panel/` folder with the agent rows, the project switcher at `components/project-switcher.svelte`, the switcher dialog, and the last-view code under `modules/panel/state/`; the scene search reuses the switcher's name match function. The 0003 spec folder on `main` (`specs/changes/0003-panel-practicality/`) holds SPEC, data model, contract, and research, but no build plan file, so the component and function names beyond `components/project-switcher.svelte` are not yet fixed anywhere. **Pending 0003 desktop merge — re-verify before T2/T3 build:** the switcher component path and its public-face export through `modules/panel/index.ts`, the name match function's exact name and file, the panel's embed of `TerminalView` with focus landing in the panel, and the last-view writer that R1 defers to. Until then, T2 and T3 must not import from `modules/panel/`.

## R3: The merged 0002 fields for role, team, team name, and team lead

**Question:** what exact field names does `floor-groups.ts` (D3) read, and from which answer?

**Findings:**

- **The agent snapshot carries no role or team.** `agent_json` in `src/modules/agent/presentation/src/mappings/entities.rs` emits `id`, `name`, `command`, `working_folder`, `project_id`, `machine_id`, `status`, `created_at`, and the gateway adds `last_line` to response agent objects (`fill_last_lines` in `src/apps/office-harnessd/src/server/agent_requests.rs`). The webview type is `Agent` in `src/apps/desktop/src/modules/agent/models/agent.ts` with the same fields, `last_line: string | null` included. No `role`, no `team_id`. The 0003 contract sentence "Where 0002 is merged, the agent snapshot below additionally carries `role` and `team`" did not happen; role and team live in the tree answer only.
- **The role, team name, and lead fields are in the `hierarchy.tree` answer.** The server shape (`tree_json` in `src/modules/hierarchy/presentation/src/handlers/hierarchy_handlers.rs`): `{ "ceo": agent | null, "teams": [team], "unassigned": [agent] }`, where a team is `{ "id", "name", "project_id", "lead": agent, "members": [agent] }` and a tree agent is `{ "id", "role", "team_id" }` (`role` is `"ceo" | "lead" | "member"` or null; the tree's role words come from `Role::as_str` in `src/modules/hierarchy/domain/src/value_objects/role.rs`). This matches the 0002 contract (`specs/changes/0002-agent-hierarchy/contracts/hierarchy-protocol.md`).
- **What the webview reader keeps:** `readHierarchyTree` and the types in `src/apps/desktop/src/modules/hierarchy/models/hierarchy.ts`. `HierarchyTreeAgent` keeps `{ id, role }` (it drops the server's `team_id`); `HierarchyTreeTeam` keeps `{ id, name, project_id, lead, members }`; `HierarchyTree` keeps `{ ceo, teams, unassigned }`. So the exact names `floor-groups.ts` reads are: `tree.teams[].name` (team name), `tree.teams[].lead.id` (team lead), `tree.teams[].members[].id`, `tree.teams[].project_id`, `tree.ceo?.id`, `tree.unassigned[].id`, and `role` on every tree agent (`"ceo" | "lead" | "member" | null`). Team membership of an agent comes from which team lists it, not from a `team_id` field the webview keeps. The tree answer carries no status, so the desk status still comes from the office snapshot (`Agent.status`, `shownStatusText`).
- **Where the webview gets the tree:** the hierarchy controller (`src/apps/desktop/src/modules/hierarchy/state/hierarchy-controller.ts`) reads `hierarchy.tree`, re-reads it on `hierarchy.changed`, and holds it as `HierarchySnapshot { phase, failure, tree }`. On `main` today the server emits `hierarchy.changed` only from the team handlers, with the causes `team.created` and `team.deleted` (`hierarchy_handlers.rs` create_team and delete_team). The contract also names `agent.placed`, `agent.unplaced`, `subtree.stopped`, and `subtree.deleted`; those four causes are contract-only on `main` (they appear in the e2e mocks, never in server code) and go live with the pending #40/#36 merges, so the scene's tree refresh may miss a re-place until then. It is a separate store from the `OfficeStore`, created beside it in `app.svelte`, so a scene that groups by team takes the tree as a second input next to `store.snapshot` (or the shell passes both). Tree updates ride `hierarchy.changed`, not the office events; a rename or re-place lands without a reload.
- **Live lines on `main`:** `agent.list` answers carry `last_line`, and the server publishes `agent.line` events `{ agent_id, line }` (`agent_line_event` in `src/modules/agent/presentation/src/mappings/events.rs`, at most once per agent per second, only when the text changed). The webview applies neither a line update nor the event yet: `modules/agent/state/` handles `agent.status`, `agent.changed`, `agent.deleted`, additions, action-record, storage, and resync only, and `agent_json` on `agent.changed` carries no `last_line`. **Pending 0003 desktop merge — re-verify before T2/T3 build:** the desktop handler that applies `agent.line` to the snapshot (0003 promised it), which the desk's in-place line update (D2) reads.

## R4: WAI-ARIA Authoring Practices for the desk pattern, the live region, and reduced motion

**Question:** which published patterns does D9 and D10 follow for a list of buttons with arrow-key movement, the polite announcements, and the reduced-motion guard?

**Findings:**

- **Keyboard: roving tabindex over a composite of buttons.** The Keyboard Interface practices page, section "Managing Focus Within Components Using a Roving `tabindex`" (`https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/`): exactly one element of the composite is in the tab sequence with `tabindex="0"`, all other focusable elements get `tabindex="-1"`; on a navigation key such as an arrow key, the script sets `tabindex="-1"` on the current element, gives `tabindex="0"` to the next one, and calls `element.focus()` on it. Tab stays floor-by-floor reading order (D9), and the arrows move within one floor through this mechanism.
- **Arrow keys over a grid of interactive elements.** The APG Grid pattern (`https://www.w3.org/WAI/ARIA/apg/patterns/grid/`) is the pattern for two-dimensional arrow-key movement over cells that hold widgets. Its sections "Keyboard Interaction For Layout Grids", "Keyboard Interaction - Setting Focus and Navigating Inside Cells", and "Whether to Focus on a Cell Or an Element Inside It" give what D9 needs: Right, Left, Up, and Down move focus one cell in their direction; when a cell contains a widget that is itself focusable, as a desk button is, focus goes to the widget, not the cell; the grid container itself is not in the tab sequence. Wrapping at row and column edges is optional for a layout grid and forbidden for a data grid; the scene floors are a layout grid, so the scene chooses and documents one behavior (D9's "within one floor" reading: no wrap past the floor's edge, arrows stop at it). The guide also notes a grid is easier to build and use when its contained widgets do not need the arrow keys themselves, which a button satisfies.
- **The polite live region.** The `status` role, WAI-ARIA 1.2 (`https://www.w3.org/TR/wai-aria-1.2/#status`), is "a type of live region providing advisory information that is not important enough to justify an alert", and elements with the role status have an implicit `aria-live` value of `polite` and an implicit `aria-atomic` value of `true` (MDN, `https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Roles/status_role`, quoting the implicit-values sentence). The `aria-live` values are `off`, `polite`, `assertive` (`https://www.w3.org/TR/wai-aria-1.2/#aria-live`). The practices add: do not move focus to the status when its content changes. So D9's one region is a single `role="status"` element present from first render, with the announcement text swapped per change; `polite` is implicit, and coalescing comes from writing the newest announcement into the same node. This is the same mechanism 0001 already ships for loading text (`role="status"` in `views/office-view.svelte`) and 0003's research R5 chose for notifications.
- **Reduced motion.** The CSS media feature `prefers-reduced-motion` has the values `no-preference` and `reduce` (MDN, `https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion`; specified in Media Queries Level 5). The WCAG 2.1 success criterion behind the guard is 2.3.3 Animation from Interactions, level AAA (`https://www.w3.org/TR/WCAG21/#animation-from-interactions`): "Motion animation triggered by interaction can be disabled, unless the animation is essential to the functionality or the information being conveyed." Its "motion animation" definition covers steps that create the illusion of movement or a smooth transition, and excludes changes of color or opacity that do not change the element's perceived size, shape, position, or distance. The scene ships no animation of its own (D10), so the criterion is met by absence; any inherited transition is guarded by a `@media (prefers-reduced-motion: reduce)` block in this change.

Verified 2026-11-18, sources `https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/`, `https://www.w3.org/WAI/ARIA/apg/patterns/grid/`, `https://www.w3.org/TR/wai-aria-1.2/#status`, `https://www.w3.org/TR/wai-aria-1.2/#aria-live`, `https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Roles/status_role`, `https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion`, `https://www.w3.org/TR/WCAG21/#animation-from-interactions`.

## R5: The Playwright reduced-motion emulation, the SC-007 scan, and the desk cut-off rule

**Question:** which API emulates `prefers-reduced-motion`, how does the SC-007 scan find a moving or flashing element, and how does a desk cut a very long line (D4)?

**Findings:**

- **The API.** `page.emulateMedia({ reducedMotion: "reduce" })` emulates the `prefers-reduced-motion` media feature; supported values are `"reduce"` and `"no-preference"`, and `null` disables the emulation. The option exists since Playwright v1.12 (`https://playwright.dev/docs/api/class-page#page-emulate-media`). The same preference is available wider than one page: as a browser context option `browser.newContext({ reducedMotion: "reduce" })` and as a test option in the config, `use: { reducedMotion: "reduce" }` (`https://playwright.dev/docs/emulation`). The office e2e runs per test, so T5 uses `test.use({ reducedMotion: "reduce" })` in the SC-007 spec, which applies to every page of those tests; `page.emulateMedia` is the per-page fallback. `matchMedia("(prefers-reduced-motion: reduce)").matches` answers true under the emulation, which the test asserts once before scanning.
- **The SC-007 scan method.** The scan runs with reduced motion emulated while 12 pushed status changes arrive (D10), then asserts that nothing moved:
  1. **Computed-style pass:** for every element inside the scene root (`sceneView.locator("*")`), read `getComputedStyle` and fail when `animationName !== "none"`, when `transitionProperty !== "none"` and `transitionDuration` is not `"0s"` on at least one side, or when `transform !== "none"`. These three are the CSS properties that produce motion; color and opacity changes without a size, shape, or position change are not motion (R4, WCAG 2.3.3 definition), so the scan does not fail on them.
  2. **Frame pass:** sample two animation frames (`page.evaluate` with two `requestAnimationFrame` calls) after the changes land and compare `getBoundingClientRect` of every desk element; fail when any rect's `x`, `y`, `width`, or `height` differs between the frames. A scrolling page moves every rect, so the scan runs without scroll input and asserts `document.scrollingElement.scrollTop` is unchanged across the two frames first.
  3. **Flashing:** the frame pass covers it at two frames; the status text changes are content changes (allowed), so the scan compares text nodes only to assert that no desk's text content swaps more than its own agent's announcement, which is the coalesced live region's job, not the desk's.
  The first pass is the deterministic one and the second proves it at runtime; both run in one spec so T7 records one result.
- **The desk cut-off rule.** A long agent name or a long last line is cut by CSS `text-overflow: ellipsis`, which "will display an ellipsis (`'…'`, `U+2026 HORIZONTAL ELLIPSIS`) to represent clipped text". The property takes effect only when the text actually overflows, which needs the pair `white-space: nowrap` and `overflow: hidden` on the same element (`https://developer.mozilla.org/en-US/docs/Web/CSS/text-overflow`). The rule for the desk: the name and the line each render in a block with `overflow: hidden; white-space: nowrap; text-overflow: ellipsis;`, one line each, so the desk keeps a fixed readable size at any width (D11) and the visible text cuts at the desk's width. The accessible name is set by hand (`aria-label`, the same mechanism the agent rows use today, `modules/agent/components/agent-list.svelte`) and always holds the full name, project, and status (D4); the last line stays visible text only and needs no accessible-name entry beyond the desk's own name. An ellipsis is a visible cut, which satisfies the spec's "cut with a visible ellipsis" without a tooltip.

Verified 2026-11-18, sources `https://playwright.dev/docs/api/class-page#page-emulate-media`, `https://playwright.dev/docs/emulation`, `https://developer.mozilla.org/en-US/docs/Web/CSS/text-overflow`.
